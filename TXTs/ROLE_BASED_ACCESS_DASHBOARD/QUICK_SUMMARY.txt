CURRENT MIDDLEWARE FLOW (How It Works Now)
===============================================================================

When a user accesses the system:

1. auth:web,employees middleware
   └─ "Are you logged in?"
   └─ Yes → Continue
   └─ No → Redirect to login

2. SetBranchContext middleware
   ├─ If Super Admin:
   │  └─ "Which branch? (Check URL, session, or default)"
   │  └─ Set session['selected_branch_id']
   │
   └─ If Employee:
      └─ "Your assigned branch is: [from database]"
      └─ Set session['selected_branch_id'] to assigned branch
      └─ Ignore any URL parameters

3. BranchMiddleware (called 'branch')
   └─ "Validate you can access that branch"
   └─ Yes → Continue
   └─ No → 403 Forbidden

4. Route handler
   └─ Display page filtered by current branch

Result: Users can only see data from their branch

WHAT'S SPECIAL ABOUT THIS SYSTEM
===============================================================================

Two-Tier User System:
  • Super Admin (web guard) - Can access all branches globally
  • Branch Staff (employees guard) - Assigned to one branch, can see all departments

Branch Switching for Super Admin:
  • Via URL parameter: ?b_id=xxx
  • Via session selection (remembers choice)
  • Via last accessed branch preference
  • Falls back to first active branch if nothing set
  • Always validated

Employee Isolation:
  • Assigned branch stored in database
  • Cannot be overridden
  • Middleware enforces it
  • Attempts logged as security warning
  • SetBranchContext always resets to assigned branch

Department Structure:
  • Each employee has a department_id
  • Departments belong to branches
  • No department switching currently
  • Future enhancement: allow filtering by department
