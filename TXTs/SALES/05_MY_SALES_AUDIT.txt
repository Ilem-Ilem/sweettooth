OVERVIEW
--------
Personal sales analytics and reporting dashboard. Shows individual employee's 
sales performance with trends, product analysis, and payment breakdowns.
Uses caching for performance.

CURRENT FUNCTIONALITY
---------------------

1. Date range selection:
   - today, yesterday, this_week, this_month, last_month
   - Manual date range possible (dateFrom, dateTo)
   - Triggers cache invalidation

2. Sales overview:
   - Total sales amount
   - Order count
   - Average order value
   - Discount total
   - Growth rate vs previous period
   - Comparison with previous period sales

3. Product analysis:
   - Top 10 selling products by revenue
   - Order count per product
   - Grouped by product_id

4. Time-based analysis:
   - Hourly sales data
   - Daily sales data with averages
   - Both within selected date range

5. Payment tracking:
   - Breakdown by payment_method
   - Total and count per method
   - Uses Payment model (if exists)

6. Order type analysis:
   - Breakdown by order_type (dine-in, takeaway, delivery)
   - Total revenue and count

7. Recent sales list:
   - Last 10 completed sales
   - With items and payment details
   - Ordered by most recent

8. Caching:
   - 5-minute TTL on computed properties
   - Manual refresh capability
   - Separate cache keys for each filter combination

INCONSISTENCIES & ISSUES FOUND
-------------------------------

❌ ISSUE 1: Caching might hide real-time changes
   Location: Lines 142, 183, etc - #[Computed] properties
   Cache: 300 seconds (5 minutes)
   Problem:
   - Sales data cached for 5 minutes
   - Might show old data to manager reviewing sales
   - No indication of when cache expires
   - Manual refresh required to see latest
   Impact: Delayed visibility of sales performance

❌ ISSUE 2: Payment model not confirmed to exist
   Location: Line 250
   Query: Payment::whereHas('sale', ...)
   Problem:
   - References Payment model
   - But ShiftClosing also uses it
   - Unclear if actually implemented
   - POS creates sales but payment tracking method unclear
   Impact: Payment breakdown might fail silently

❌ ISSUE 3: Growth rate calculation misleading
   Location: Lines 155-167
   Formula: (current - previous) / previous * 100
   Problem:
   - Compares current period against equal-length previous period
   - But for 'today' period: previous is yesterday
   - That's only 1 day back, not meaningful comparison
   - Should compare to same day last week/month instead
   Impact: Daily growth rates might show false trends

❌ ISSUE 4: Date range calculation complex
   Location: Lines 111-137 (setDateRange method)
   Problem:
   - Multiple date formats (H:i:s included)
   - Inconsistent with what Carbon::now() vs Carbon::parse() expect
   - Using startOfDay/endOfDay vs explicit H:i:s strings
   Impact: Potential date filtering edge cases

❌ ISSUE 5: Comparison period might overlap
   Location: Line 157-158
   Current:
   - $prevFrom = $dateFrom - period_length days
   - $prevTo = $dateFrom - 1 second
   Problem:
   - If dateFrom is today 00:00:00, subtracting 1 second gives yesterday 23:59:59
   - Works but fragile
   - If dateFrom is mid-day, calculation wrong
   Impact: Comparison period calculations unreliable

❌ ISSUE 6: No branch/department filtering validation
   Location: mount() method
   Problem: No error if branch or department not loaded
   Current: Just uses them if set
   Impact: Might show all employees' sales if branchId missing

❌ ISSUE 7: Cache key includes timestamps
   Location: Lines 293-303 (getCacheKey)
   Issue: Cache key includes full dateFrom/dateTo strings
   Problem:
   - Different query variations create different cache entries
   - Cache never accumulates expiry - manual cleanup only
   - Could cause cache bloat
   Impact: Cache memory usage unbounded

❌ ISSUE 8: No error handling on Payment model
   Location: Line 250
   Problem: If Payment table missing, throws exception
   Impact: Module fails completely

❌ ISSUE 9: Top products might not show all products
   Location: Line 200
   Limit: limit(10)
   Problem:
   - Only shows top 10 by revenue
   - Lower-selling products hidden
   - No pagination for additional products
   Impact: Incomplete view of product performance

❌ ISSUE 10: Hourly data loses context on multi-day queries
   Location: Lines 206-223 (hourlySalesData)
   Problem:
   - Groups by HOUR() only
   - Multiple days show aggregated hours (0-23)
   - Day 1 hour 10 mixed with Day 2 hour 10
   - Should include DATE() in grouping
   Impact: Misleading hourly charts for multi-day ranges

❌ ISSUE 11: Recent sales limit hard-coded
   Location: Line 289
   Limit: limit(10)
   Problem:
   - Only shows 10 recent sales
   - No pagination
   - No way to view more sales history
   Impact: Limited historical view

❌ ISSUE 12: Order type breakdown might miss types
   Location: Lines 265-277
   Query: ORDER TYPE = specific value
   Problem:
   - Groups by order_type but no coalesce/fallback
   - NULLs or unknown values might not group correctly
   - Should validate order_type field values
   Impact: Missing order types in breakdown

❌ ISSUE 13: No data validation
   Location: mount() method
   Problem:
   - No check if employeeId is valid
   - No check if assigned to department
   - No check if branch access allowed
   Impact: Potential security issue - could view other employee's sales

❌ ISSUE 14: Date range doesn't validate bounds
   Location: setDateRange() method
   Problem:
   - Allows any date range without validation
   - Could set dateFrom > dateTo
   - No minimum/maximum bounds
   Impact: Malformed queries if wrong dates set

❌ ISSUE 15: refreshData() doesn't unset computed properties correctly
   Location: Lines 312-317
   Method: unset($this->computed_property)
   Problem:
   - Unsetting might not work on #[Computed] properties
   - Livewire might cache computed values differently
   - Should use cache invalidation instead
   Impact: Manual refresh might not work

PERFORMANCE ISSUES
------------------

1. Complex queries:
   - Lines 184-201: Multiple joins for top products
   - Lines 228-243: Daily grouping query
   - Lines 249-261: Payment breakdown requires join
   Impact: Slow page load if many sales

2. No query optimization:
   - No eager loading
   - No select() limiting fields
   - Fetches all columns then filters

3. Cache still queries database:
   - Even with cache, computed properties still run
   - Cache remembers the result only
   Impact: First load or after cache expiry slow
