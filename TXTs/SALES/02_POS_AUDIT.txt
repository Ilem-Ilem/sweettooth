OVERVIEW
--------
Main point-of-sale system handling sales transactions, cart management, 
payment processing, and table management for dine-in operations.

CURRENT FUNCTIONALITY
---------------------

1. Stock verification:
   - Checks if stock opening has been completed for department/shift
   - Redirects to stock opening if not verified
   - Department-level verification (any employee can open stock)

2. Cart management:
   - Add/remove/increment/decrement items
   - Quantity validation against available stock
   - Strict enforcement: cannot exceed available quantity

3. Product display:
   - Filtered by department products
   - Search by name/SKU
   - Real-time availability checking

4. Payment processing:
   - Multiple payment methods (cash, transfer, pos)
   - Multiple payment rows support
   - Change calculation

5. Order types:
   - dine-in
   - takeaway
   - delivery

6. Sales workflow:
   - Complete sale (immediate payment)
   - Hold sale (draft, no stock impact)
   - Resume held sale

7. Table management:
   - Toggle table management per department
   - Create/delete/toggle table status
   - Save table tabs (pending orders)
   - Complete table sale (process payment)

INCONSISTENCIES & ISSUES FOUND
-------------------------------

❌ ISSUE 1: Missing active shift validation on POS start
   Location: mount() method, line 77
   Problem: loadActiveShift() called but no error if shift is null
   Impact: POS loads without requiring active shift, unlike stock opening
   Note: completeSale() method checks for active shift (line 447)
   Inconsistency: Should enforce active shift in mount()

❌ ISSUE 2: Stock verification logic inconsistency
   Location: checkStockVerification() method, lines 171-210
   Problem: Checks for existing ProductStock records but logic is unclear:
   - Counts ProductStock records for department/shift/date
   - Returns true if ANY products have stock records
   - But doesn't verify ALL products have been opened
   Impact: Could allow POS access if only one product was opened

❌ ISSUE 3: Department-level vs Employee-level stock opening
   Location: Lines 173-175 comments
   Comment: "department-level, not employee-level"
   Problem: Not enforced - any employee can verify stock for all
   Impact: One employee might open stock with inaccurate counts
   Related: Should add employee accountability

❌ ISSUE 4: Hard-coded shift type
   Location: Line 186
   Issue: $shiftType = $shift?->shift_type ?? 'morning'
   Problem: Assumes 'morning' default, but may have afternoon/evening shifts
   Impact: Stock verification might check wrong shift

❌ ISSUE 5: table_management flag vs actual table existence
   Location: toggleTableManagement() method, lines 212-252
   Issue: Enables table management and creates default 8 tables
   Problem: No consistency check if tables are manually deleted
   Impact: Table references could break if tables are removed

❌ ISSUE 6: Cart state inconsistency on branch change
   Location: handleBranchChange() method, line 107
   Issue: Calls resetCart() on branch change
   Problem: No warning to user about clearing cart
   Impact: Data loss without user confirmation

❌ ISSUE 7: Sales not linked to shift
   Location: completeSale() method, lines 470-471
   Current: sales_shift_id = null
   Problem: Sales are not linked to the actual Shift record
   Impact: Cannot track which employee made the sale at shift time
   Note: sold_by field exists (line 474) but not shift linkage

❌ ISSUE 8: Stock locking mechanism inadequate
   Location: getTodayStockForProduct() method, line 657
   Issue: Uses lockForUpdate() only in completeSale()
   Problem: Race condition possible if multiple employees process sales simultaneously
   Impact: Double-selling possible in high-concurrency scenarios

❌ ISSUE 9: Payment methods validation inconsistency
   Location: Line 68 rules vs completeSale() validation
   Rules allow: 'cash', 'transfer', 'pos'
   But: Receipt builds payments assuming these methods (line 684)
   Problem: No validation that payment methods in cart match allowed types

❌ ISSUE 10: Missing order number in hold sales
   Location: holdSale() method, line 578
   Issue: Uses 'HOLD-' prefix for numbering
   Problem: Held sales not tracked separately in reporting
   Impact: Difficult to distinguish held vs completed vs abandoned orders

WORKFLOW GAPS
-------------

1. No audit trail for POS operations
2. No till reconciliation or shift opening/closing for POS
3. No refund workflow
4. No modifier support (extra toppings, customizations)
5. No discount reason tracking
6. No inventory recount during shift
7. No product expiry warnings during sale
8. No concurrent user warnings (multiple employees on POS)

DATA INTEGRITY ISSUES
---------------------

1. Receipt storage:
   - Receipt stored per sale (good)
   - But stores raw HTML in database (scaling issue)
   - No print history or reprint capability

2. Stock calculation:
   - Available quantity uses closing_quantity
   - But closing_quantity updated after sale completes
   - Should use real-time calculation

3. Partial fulfillment:
   - completeSale() handles stock shortage (lines 496-500)
   - Silently reduces quantity if stock runs out
   - Should warn user before proceeding

TABLE MANAGEMENT ISSUES
----------------------

1. No table status persistence
   - table->status field exists but not fully used
   - Uses 'occupied' vs 'available' vs 'reserved'

2. No order assignment to specific waiters
   - No way to track which employee opened order

3. No table merging capability
   - Cannot combine multiple tables for party orders

4. No reserved/blocked table states
   - Cannot block table for cleaning/maintenance

PERFORMANCE ISSUES
------------------

1. Real-time stock queries in cart rendering
   - getTodayStockForProduct() called for every product on render
   - Should cache or batch query

2. Complex payment array management
   - No database structure for payment breakdown
   - Stored as JSON in receipt meta

RECOMMENDATIONS
---------------

1. Enforce active shift requirement in mount()
   - Add error toast if no active shift
   - Redirect to clock-in if needed

2. Fix stock verification logic:
   - Check that ALL department products have been opened
   - Add minimum stock count requirement

3. Add shift linking to sales:
   - Add sales_shift_id or shift_id relationship
   - Maintain employee shift accountability

4. Implement pessimistic locking:
   - Lock ProductStock during completeSale()
   - Prevent race conditions

5. Add refund workflow:
   - Track refunded items in separate table
   - Update stock on refund

6. Add table status workflow:
   - Reserved (for future)
   - Cleaning (blocked)
   - Occupied (with sale)
   - Available (empty)

7. Add payment reconciliation:
   - Create till opening/closing workflow
   - Separate from inventory closing

8. Add audit trail:
   - Log all POS operations
   - Track discounts, voids, refunds

9. Improve partial fulfillment:
   - Confirm with user before reducing quantity
   - Option to backorder remaining items

10. Add product warnings:
    - Expiry date warnings
    - Low stock warnings
    - Out of stock blocking
