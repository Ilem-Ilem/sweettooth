COMPLETE SALES WORKFLOW FLOW
----------------------------

1. SHIFT START (Employee clocks in)
   └─ Shift record created in shifts table with status='active'

2. STOCK OPENING (Department-level, before POS access)
   └─ Employee navigates to StockOpening
   └─ Selects or uses active shift
   └─ System loads:
      - Yesterday's closing (ProductStock from previous day)
      - Today's additions (from production_records via production_dispatch)
      - Expected opening = yesterday's closing
   └─ Employee enters actual opening count
   └─ System calculates variance
   └─ Employee clicks SAVE
   └─ ProductStock records created with:
      - opening_quantity (actual count)
      - addition_quantity (from production)
      - total_available = opening + additions
      - closing_quantity initialized = total_available
   └─ Department can now access POS

3. SALES (Point of Sale)
   └─ POS module checks: Stock opening exists for department
      └─ If not, redirects to StockOpening
   └─ Employee adds products to cart
   └─ System checks availability from ProductStock.closing_quantity
   └─ Employee pays
   └─ System creates Sale record with:
      - sale_time, total, discount, sold_by, branch_id, department_id
      - status='completed'
      - order_type (dine-in/takeaway/delivery)
   └─ For each item, creates SaleItem record with:
      - quantity, unit_price, total
   └─ System updates ProductStock:
      - quantity_sold += quantity
      - closing_quantity = opening + additions - total_sold
   └─ Creates Receipt record

4. PRODUCTION DISPATCH (Happens during shift)
   └─ Production sends dispatch for products
   └─ Dispatch created in ProductDispatch table
   └─ Dispatch record has:
      - product_id, quantity, dispatch_date, shift_type
      - status='dispatched'
   └─ Appears in Dispatches module in Sales
   └─ Sales employee receives dispatch:
      - Opens receiving modal
      - Enters received quantity (might differ from sent)
      - Adds receiving notes
   └─ Updates ProductDispatch status to 'received'
   └─ Updates ProductStock:
      - addition_quantity += received_quantity
      - closing_quantity = opening + total_additions - sold
   └─ Or creates new ProductStock if not exists

5. SHIFT CLOSING (End of shift)
   └─ Employee navigates to ShiftClosing
   └─ System loads:
      - All ProductStock records for today
      - Expected closing = opening + additions - sold
      - Actual closing = entered manually (defaults to expected)
   └─ System loads all sales for shift
   └─ Calculates sales totals, discounts, payment breakdown
   └─ System loads expected cash/pos/transfer from Payment table
   └─ Employee enters actual cash/pos/transfer counts
   └─ System calculates variances
   └─ If variance > threshold, requires variance reason
   └─ Employee submits closing
   └─ System:
      - Creates Callback for stock variances > 0
      - Creates Callback for expired items
      - Updates ProductStock closing_quantity with actual count
      - Updates Shift status='closed', clock_out=now()
      - Stores reconciliation data in shift.notes (JSON)

6. REPORTING (My Sales module)
   └─ Employee can view personal sales summary
   └─ Cached for 5 minutes
   └─ Shows: totals, growth, top products, payment breakdown
   └─ Can manually refresh cache

CRITICAL WORKFLOW ISSUES
========================

CRITICAL ISSUE #1: Missing Shift Linking in Sales
--------------------------------------------------
Impact Level: HIGH - Data Integrity

Problem:
- Sales created without linking to Shift record
- Sale has sold_by (employee ID) but no shift_id
- Cannot determine which shift a sale belongs to
- Employee could manually date sales to wrong shift

Current Code (POS/Index.php, line 471):
  'sales_shift_id' => null,

Data Loss Risk:
- Historical sales cannot be attributed to specific shifts
- Shift closing cannot properly validate sales
- Sales reports cannot be per-shift
- Cannot prevent post-shift sales entry

Solution Required:
  1. Add shift_id field to Sale table
  2. Set shift_id = current active shift on sale creation
  3. Enforce shift_id on update (prevent tampering)
  4. Use shift.clock_in/clock_out for time validation
  5. Link Sale items to shift for payment reconciliation

Affected Modules:
- POS: completeSale(), holdSale()
- ShiftClosing: Sales queries assume date-based filtering
- MySales: Reports by employee only, not by shift

CRITICAL ISSUE #2: Production Additions Not Validated
------------------------------------------------------
Impact Level: HIGH - Data Integrity

Problem:
- Stock opening loads additions from production_records table
- Matches by recipe.product_name = product.name (TEXT string match!)
- If production_records table doesn't exist, silently fails to 0
- If recipe name differs from product name, missing data
- No way to verify additions match actual dispatches

Current Code (StockOpening/Index.php, lines 256-305):
  WHERE recipes.product_name = products.name (fragile name match)
  Try-catch silently returns $todayAdditions = 0 on error

Data Loss Risk:
- Products with no matching recipe name show 0 additions
- But ProductDispatch records show actual dispatches
- Stock opening shows zero, but dispatch received later
- Creates variance variance blamed on employee

Correct Data Source:
- ProductDispatch with status='received' is reliable
- Already verified by sales employee
- Has dispatch_date, shift_type, quantity

Solution Required:
  1. Use ProductDispatch as primary source for additions
  2. Filter by: status='received', dispatch_date=today, shift_type=current
  3. Sum received quantity per product
  4. Remove production_records dependency

Affected Modules:
- StockOpening: loadStockOpeningData() method
- ShiftClosing: closing_quantity calculations

CRITICAL ISSUE #3: Stock Verification Bypass in POS
---------------------------------------------------
Impact Level: HIGH - Operational Control

Problem:
- POS checks if stock opening exists with checkStockVerification()
- But logic only checks if ANY ProductStock exists
- Doesn't verify ALL products have been counted
- Doesn't check counts are accurate/complete

Current Code (POS/Index.php, lines 171-210):
  $stockCount = ProductStock::whereDate('stock_date', Carbon::today())
      ->where('shift_type', $shiftType)
      ->whereIn('product_id', $productIds)
      ->count();
  return $stockCount > 0;

Risk:
- If only 1 of 10 products counted, POS still accessible
- If counts entered incorrectly, no validation
- Employee can override stock opening without checking
- Sales allowed with incomplete/wrong stock data

Solution Required:
  1. Add is_verified flag to ProductStock
  2. Verify flag set only after deliberate save action
  3. Check ALL department products have is_verified = true
  4. Prevent sales until all products verified
  5. Add status field to track verification completion

Affected Modules:
- POS: checkStockVerification() method
- StockOpening: Set is_verified on save
- ShiftClosing: Use is_verified status

CRITICAL ISSUE #4: Sales Timestamp vs Shift Boundaries
------------------------------------------------------
Impact Level: MEDIUM - Data Integrity

Problem:
- Shift has clock_in and clock_out times (or should)
- But no validation that sales occur within shift time
- Shift Closing queries by date, not by shift times
- ShiftClosing might miss sales at shift end, gain from next shift start

Current Code (ShiftClosing/Index.php, lines 215-221):
  $shift->clock_in ?? $shift->shift_date->startOfDay()
  Uses shift times for querying sales

Risk:
- Sales entered before clock_in not caught
- Sales entered after clock_out counted in wrong shift
- Night shifts spanning midnight counted wrong
- Closing totals inaccurate

Solution Required:
  1. Enforce sale_time is between shift.clock_in and shift.clock_out
  2. Prevent sales entry after shift closed
  3. Allow sales modification only during active shift
  4. Query by shift times, not by date

Affected Modules:
- POS: Add shift time validation on sale creation
- ShiftClosing: Use shift times not date for filtering

CRITICAL ISSUE #5: Cash Reconciliation Uses Non-existent Data
-------------------------------------------------------------
Impact Level: MEDIUM - Operational

Problem:
- ShiftClosing expects Payment model/table
- But unclear if Payment table exists
- POS creates sales with payment_method, amount in JSON receipt
- ShiftClosing queries Payment table (which might not exist)
- Two separate payment tracking systems?

Current Code (ShiftClosing/Index.php, lines 307-320):
  $payments = Payment::whereHas('sale', function($q) use ($shift) {...})

Code also references (POS/Index.php, lines 533):
  'payments' => $this->payments, (stored in receipt meta as array)

Risk:
- Cash reconciliation might fail if Payment table missing
- Payment data might be lost if only in JSON
- Two sources of truth for payments
- Cannot reconcile

Solution Required:
  1. Clarify if Payment model/table should exist
  2. If yes: ensure payments create Payment records on sale
  3. If no: update ShiftClosing to read from receipt JSON
  4. Create single source of truth for payment data
  5. Add validation that payment total = sale total

Affected Modules:
- POS: Create Payment records on sale completion
- ShiftClosing: Use single payment data source
- Reporting: Use consistent payment data

CRITICAL ISSUE #6: Batch Receive vs Incremental Receive Confusion
-----------------------------------------------------------------
Impact Level: MEDIUM - Data Integrity

Problem:
- ProductDispatch: Sent in batches from production
- Sales receives one dispatch at a time
- But StockOpening tries to auto-load additions from production
- Creates duplicate/conflict: dispatch record vs production record

Current Flow:
1. Production sends: ProductDispatch created (quantity=100)
2. StockOpening loads additions from production_records (quantity=100)
3. Sales receives: ProductDispatch status='received'
4. ShiftClosing uses ProductStock.addition_quantity (from StockOpening)
5. But actual received might be different!

Risk:
- Dispatch sent (100), but only received (90) by sales
- StockOpening shows 100 (from production_records)
- Actual received (90), variance blamed on sales
- Data inconsistency between systems

Solution Required:
  1. Use ProductDispatch as single source for additions
  2. StockOpening should reference dispatches already received
  3. Not pre-load from production, wait for actual receipt
  4. More transparent: what's sent vs what's received

Affected Modules:
- StockOpening: loadStockOpeningData() - use dispatches instead of production
- Dispatches: receiveDispatch() - update ProductStock properly
- ShiftClosing: Use actual received, not planned

CRITICAL ISSUE #7: Terminology Inconsistency
--------------------------------------------
Impact Level: LOW - User Confusion

Problem:
- All modules refer to "Kitchen Dispatch" (old name)
- Should be "Production Dispatch" (new standard)
- UI shows "Dispatch Receiving" not "Production Dispatch Receiving"
- Creates confusion between order dispatch (logistics) and product dispatch

Locations:
- Dispatches/Index.php line 32: departmentName = 'Dispatch Receiving'
- Dispatches/Index.php line 250: notes = 'Received from kitchen dispatch'
- Multiple other references throughout code

Impact:
- User confusion on what "dispatch" means
- Inconsistent with production terminology
- Makes onboarding harder
- Documentation becomes misleading

Solution Required:
  1. Global find/replace: "kitchen dispatch" → "production dispatch"
  2. Update UI labels consistently
  3. Update database comments/docs
  4. Update user documentation

CRITICAL ISSUE #8: No Audit Trail of Financial Changes
------------------------------------------------------
Impact Level: MEDIUM - Compliance

Problem:
- Sales can be deleted/modified with no tracking
- Cash reconciliation changes not logged
- Stock variances not investigated
- No who/when/why for financial transactions

Risk:
- Fraud detection impossible
- Cannot audit shift closing
- Cannot investigate missing cash
- Regulatory compliance failure

Solution Required:
  1. Add audit_logs table
  2. Log all financial transactions (sales, payments, variances)
  3. Track who made each change and when
  4. Store original values for comparison
  5. Implement immutable sales records after close
