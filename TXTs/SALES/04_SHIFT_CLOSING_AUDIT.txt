OVERVIEW
--------
Manages end-of-shift reconciliation for sales department. Includes stock 
closing verification, sales summary, cash reconciliation, and variance 
tracking. Creates callbacks for variances and expired items.

CURRENT FUNCTIONALITY
---------------------

1. Closing stock data:
   - Opening quantity (from ProductStock)
   - Additions (from ProductStock)
   - Sold quantity (calculated from SaleItems)
   - Expected closing = opening + additions - sold
   - Actual closing = manual entry (defaults to expected)
   - Variance = actual - expected
   - Expiry flag based on expiry_date

2. Sales summary:
   - Total sales, orders, discount, tax
   - Cancelled order count
   - Payment method breakdown
   - Top 5 products by quantity
   - Order type breakdown (dine-in, takeaway, delivery)

3. Cash reconciliation:
   - Expected amounts by payment method (cash, pos, transfer)
   - Actual amounts entered manually
   - Variance calculation with threshold alerts
   - Variance reason tracking when exceeds threshold

4. Callbacks:
   - Automatic for stock variances
   - Automatic for expired items
   - Stores as Callback records

5. Shift closure:
   - Updates shift status to 'closed'
   - Sets clock_out timestamp
   - Stores reconciliation data in JSON
   - Updates product stock records with closing quantities

INCONSISTENCIES & ISSUES FOUND
-------------------------------

❌ ISSUE 1: Missing shift validation on module load
   Location: mount() method
   Problem: No error if currentShift is null or not found
   Impact: Module loads but cannot save without shift
   Related: POS enforces active shift, this doesn't

❌ ISSUE 2: Shift date vs closing date ambiguity
   Location: Multiple places reference $this->shiftDate
   Problem:
   - Initialized from Carbon::today() in mount()
   - But never updated if shift was on different date
   - Closing data queried by shift_date from loaded shift
   - Could close shift from different day if loaded late
   Impact: Historical shift closing could corrupt data

❌ ISSUE 3: Hard-coded shift type default
   Location: Line 38
   Issue: $shiftType = 'morning'
   Problem: If shift.shift_type is missing, defaults to morning
   Impact: Afternoon/evening closings might use wrong data

❌ ISSUE 4: Sold quantity calculation might miss sales
   Location: Lines 160-167
   Query: SaleItem WHERE sale NOT cancelled AND product_id = ?
   Problem:
   - Uses sale_time query but shift_date used for stock_date
   - Shift might span multiple calendar days (long/night shift)
   - Query uses exact date only
   - Should use shift clock_in/clock_out times instead
   Impact: Multi-day shifts lose sales from crossing midnight

❌ ISSUE 5: Expected closing calculation incorrect for multi-day
   Location: Line 170
   Formula: opening + additions - sold
   Problem:
   - opening_quantity is START of shift
   - additions might be received during shift
   - But if shift crosses midnight, additions = next day's
   - Formula still mathematically correct but conceptually wrong
   Impact: Closing variance inflated for night shifts

❌ ISSUE 6: Hard-coded currency and threshold
   Location: Lines 326-329
   Issue: Max(100, expectedCash * 0.01) with no currency indicator
   Problem:
   - Currency is implicit (no field check)
   - 100 units might be too high/low depending on currency
   - 1% threshold arbitrary, no business rule
   - Should be configurable per branch
   Impact: Thresholds might not alert appropriately

❌ ISSUE 7: Payment table doesn't exist
   Location: Line 307
   Query: Payment::whereHas('sale', ...)
   Problem:
   - Code refers to Payment model
   - But sales use payments array in receipt JSON
   - Two separate payment tracking systems?
   - Inconsistent with POS code
   Impact: Cash reconciliation might not work if Payment table missing

❌ ISSUE 8: Missing employee accountability
   Location: saveShiftClosing() method
   Problem: No field to track who closed the shift
   Current: Just saves to shift.notes as JSON
   Impact: Cannot audit who performed closing

❌ ISSUE 9: Callback creation for variance
   Location: Lines 441-453
   Issue: Creates callback for ANY variance > 0
   Problem:
   - Even +1 item creates callback (excess)
   - Should have minimum threshold
   - Excess items might be intentional stock replenishment
   - Not all variances are "callbacks"
   Impact: Excessive callback records

❌ ISSUE 10: Expired product callback status
   Location: Lines 456-469
   Issue: Expired product callback has status = 'approved'
   Problem:
   - Other variances are 'pending'
   - Inconsistent approval workflow
   - Approved implies someone verified/approved it
   - But just auto-created from system data
   Impact: Audit trail confusion

❌ ISSUE 11: Variance threshold logic might not trigger
   Location: Lines 405-418 validation
   Problem:
   - Checks if $this->cashReconciliation['cash_requires_reason']
   - But cashReconciliation recalculated in loadCashReconciliation()
   - Which is called in updated() handler
   - But saveShiftClosing() doesn't call updated()
   - So stale values used for validation
   Impact: Variance reason validation might not work

❌ ISSUE 12: No reconciliation status tracking
   Location: No isReconciled or reconciliation_status field
   Problem:
   - Shift just closed with status = 'closed'
   - No indication if reconciliation was successful/pending/failed
   - Cannot distinguish incomplete vs complete closings
   Impact: Unclear shift closure quality

❌ ISSUE 13: Quantity sold calculation might be wrong type
   Location: Line 161
   Query: sum('quantity')
   Problem:
   - SaleItem.quantity might be decimal/float
   - ProductStock expects numeric
   - SUM returns 0 if no records
   - Should explicitly cast
   Impact: Type mismatch in closing calculation

❌ ISSUE 14: Expired item expiry_date check
   Location: Lines 182-184
   Issue: Checks expiry_date <= now()
   Problem:
   - Now() returns current timestamp with time
   - Expiry_date is likely date only (no time)
   - Comparison includes time component
   - Should use diffInDays instead
   Impact: Expiry check might be off by timezone/hour

❌ ISSUE 15: Missing department validation
   Location: loadClosingData() method
   Problem: No check if departmentId is valid/loaded
   Current: Just uses it if set
   Impact: Wrong department data if not loaded properly

WORKFLOW GAPS
-------------

1. No stock recount during closing
   - Just uses count from opening
   - No actual count verification at close

2. No settlement workflow
   - Cash counted but not handed over
   - No receipt/sign-off from manager

3. No shift opening/closing period enforcement
   - Can close same shift multiple times
   - No lock on closed shifts

4. No till reconciliation
   - Cash reconciliation but no physical till
   - No integration with payment system

5. No report generation
   - Summary calculated but not saved as report
   - Cannot access historical summaries

6. No exception handling for large variances
   - Just requires reason
   - No escalation or investigation trigger

7. No variance investigation workflow
   - Just notes, no root cause tracking
   - No follow-up actions

DATA INTEGRITY ISSUES
---------------------

1. Stock calculation across shifts:
   - Assumes single shift per day per department
   - Morning/afternoon shifts might both need closing
   - Only one closing per date stored

2. Payment reconciliation:
   - Expected vs actual based on Payment table
   - But might not exist or be inconsistent
   - Receipt stores payments in JSON

3. Sale time filtering:
   - Uses sale_time between shift times
   - But uses $shiftDate for stock lookup
   - Mismatch if shift crosses midnight

4. Callback creation timing:
   - Created during closing
   - But variance might be from previous shift
   - Should have more context

5. Notes storage:
   - Stored as JSON in shift.notes
   - No validation schema
   - No versioning if updated
