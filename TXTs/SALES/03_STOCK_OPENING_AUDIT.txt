OVERVIEW
--------
Manages opening stock verification for sales shift. Employees count actual 
opening stock, compare with expected (previous day's closing), and verify 
production additions before sales can proceed.

CURRENT FUNCTIONALITY
---------------------

1. Data loading:
   - Yesterday's closing stock (from previous ProductStock)
   - Today's production additions (from production_records joined with dailyProduce)
   - Expected opening = yesterday's closing
   - Actual opening = manual count (defaults to expected)

2. Variance tracking:
   - Calculated: actual opening - expected opening
   - Identifies stock count differences from previous day

3. Production record integration:
   - Joins production_records → daily_produces → shifts → recipes
   - Matches by recipe.product_name = product.name
   - Sums quantity_approved (approved yield) for additions

4. Time-based navigation:
   - View past 30 days of shifts
   - Select different shift to view historical data
   - Current active shift loaded on mount

5. Manual verification:
   - Update actual opening quantities
   - Update production dates
   - Add notes per product
   - Auto-calculate expiry dates from production_date + shelf_life_days

6. Data persistence:
   - Save all stock openings in single transaction
   - Sets opening_quantity and addition_quantity in ProductStock
   - Calculates total_available = opening + additions

INCONSISTENCIES & ISSUES FOUND
-------------------------------

❌ ISSUE 1: Production record matching by name is fragile
   Location: Lines 257-275 (loadStockOpeningData method)
   Query: WHERE recipes.product_name = products.name
   Problem: 
   - Match is by TEXT string, not ID relationship
   - Product name could change, breaking historical records
   - No foreign key constraint
   - Brittle to typos in recipe product_name field
   Impact: Missing or duplicate production additions for products

❌ ISSUE 2: Missing database table check
   Location: Lines 256-305
   Try-catch silently ignores errors:
   - production_records table might not exist
   - daily_produces table might not exist
   - Silently falls back to $todayAdditions = 0
   Problem: No logging or user notification of schema issues
   Impact: Stock opening silently shows zero additions

❌ ISSUE 3: Quantity field ambiguity
   Location: Lines 278-279
   Using: $record->quantity_approved ?? 0
   Also available: quantity_sent_out, quantity_produced, quantity_rejected
   Problem:
   - Code suggests 'quantity_sent_out' is what goes to sales
   - But uses 'quantity_approved' instead
   - Comment on line 278: "Use yield produced (quantity_approved) not batch"
   - Unclear which field is actually correct
   Impact: Additions might be calculated from wrong values

❌ ISSUE 4: Yield percentage calculation unused
   Location: Lines 282-294
   Calculates: $yieldPercentage but only stores in array
   Problem: Data calculated but not displayed or validated
   Impact: Overhead calculation with no benefit

❌ ISSUE 5: Shift selection vs actual shift mismatch
   Location: updatedSelectedShiftForViewing() method, lines 161-171
   Issue: User can view any past shift but saved data goes to current shift
   Problem:
   - User views yesterday's data
   - But when they save, it saves to TODAY's current shift
   - Could cause data loss or overwrite
   Impact: User confusion on which shift they're saving for

❌ ISSUE 6: Opening quantity source is ambiguous
   Location: Lines 320
   Current: $actualOpening = $todayStock ? $todayStock->opening_quantity : $yesterdayClosing
   Problem:
   - If stock exists, uses stored opening_quantity (already verified?)
   - If not, defaults to yesterday's closing (assumed opening)
   - But employee might be changing the default
   - No indicator of whether this was already saved
   Impact: Opening quantity could be re-verified multiple times

❌ ISSUE 7: Missing employee accountability
   Location: saveStockOpenings() method, lines 413-453
   Problem: No tracking of which employee performed verification
   Current: Uses updateOrCreate with no employee_id field
   Impact: Cannot audit who verified stock

❌ ISSUE 8: Shift type hard-coded default
   Location: Line 41, 197
   Issue: $shiftType = $shift?->shift_type ?? 'morning'
   Problem: If shift_type field missing, defaults to 'morning'
   Impact: Afternoon/evening shifts might be queried as morning

❌ ISSUE 9: No previous stock found handling
   Location: Line 246
   If yesterday's stock not found:
   - $yesterdayClosing = 0
   - Assumes first day of operation
   - No special handling or warning
   Problem: Day 2 of operation shows variance as opening stock
   Impact: Inflated variance reports for new locations

❌ ISSUE 10: Sales shift vs general shift confusion
   Location: Lines 310, 464
   Issue: Saves to sales_shift_id but no clear relationship
   Also: ProductStock.stock_date and shift_type already identify the shift
   Problem: Redundant vs unclear shift identification
   Impact: Data model confusion

❌ ISSUE 11: No department product validation
   Location: Lines 215-227
   Uses: Product::query()->forDepartment($this->departmentId)
   Problem:
   - Department might have many products
   - But only some produced today
   - Shows all products in list anyway
   - Creates "zero additions" entries for products not produced
   Impact: Cluttered list with non-produced items

❌ ISSUE 12: Stock opening verification loop in POS
   Location: Circular dependency check
   - POS checks if stock has been opened (checkStockVerification)
   - But checkStockVerification only counts ProductStock records
   - Could be opened but incomplete/incorrect
   Problem: No quality validation of stock opening data
   Impact: POS could proceed with incomplete stock counts

WORKFLOW GAPS
-------------

1. No stock re-verification during shift
   - Stock counts can change during day due to damage/loss
   - No mechanism to recount during shift

2. No damage/loss recording
   - Only opening and closing counts exist
   - No tracking of mid-shift damage

3. No bulk stock adjustment
   - Must edit each product individually
   - No import/export capability

4. No approval workflow
   - Any employee can verify stock
   - No manager approval required

5. No stock reconciliation meeting/sign-off
   - Just saves data, no formal closing

6. No variance threshold alerts
   - High variances not flagged for investigation

DATA INTEGRITY ISSUES
---------------------

1. Production record matching failure:
   - Missing recipes in dailyProduce
   - Product name mismatches
   - Lost production additions

2. Stock calculations:
   - opening_quantity defaults to yesterday's closing
   - But then employee changes it
   - No audit of what changed and why

3. Production date source:
   - Uses todayStock.production_date if exists
   - Otherwise defaults to today
   - But actual production might be yesterday

4. Expiry date calculation:
   - Only if product.shelf_life_days > 0
   - Otherwise null
   - Some products might have unknown shelf life

RELATED SYSTEMS ISSUES
---------------------

1. POS Stock Checking Dependency:
   - POS redirects here if stock not opened
   - Tight coupling between modules
   - Should have event/listener pattern instead

2. Production Dispatch Dependency:
   - Expected additions come from production_records
   - But dispatch might fail to complete
   - Missing dispatches = missing additions

3. Shift System Dependency:
   - Requires active shift to save
   - But allows viewing without active shift
   - Inconsistent enforcement

RECOMMENDATIONS

1. Create proper foreign key for production linking:
   - Add product_id to DailyProduce table
   - OR add daily_produce_id to ProductStock
   - Replace name-based matching with FK

2. Add employee tracking:
   - Add verified_by (employee_id) field
   - Add verified_at timestamp
   - Maintain audit trail

3. Add quality validation:
   - Flag variances > threshold
   - Require reason for large variances
   - Escalate to manager if needed

4. Improve production record integration:
   - Add status to track which batches sent to sales
   - Create explicit dispatches in stock opening
   - Link dispatches to production records

5. Add stock opening approval workflow:
   - Manager approval required for high variances
   - Formal sign-off by responsible person
   - Close-out date/time enforcement

6. Improve shift handling:
   - Prevent viewing past shifts in edit mode
   - Only allow editing current shift's opening
   - Archive historical data separately

7. Add variance investigation:
   - Root cause codes (damage, theft, spoilage, count_error)
   - Investigation notes field
   - Follow-up actions

8. Improve production additions accuracy:
   - Use ProductDispatch.status = 'received' as source
   - Replace production_records query with dispatch records
   - More reliable and already verified by sales

9. Add bulk operations:
   - Adjust multiple products at once
   - Template for repeat items
   - Rapid entry mode

10. Add reporting:
    - Variance by product over time
    - Variance by shift/employee
    - Production additions accuracy
    - Historical trends
