============================

- ProductDispatch model ✓ (correct)

SHIFT SYSTEM CONSISTENCY
========================

SHIFT CREATION:
Location: HeaderClockInOut.php (or similar)
Creates: Shift record in shifts table
Fields: employee_id, shift_date, shift_type, status='active', clock_in, clock_out
Branch: shift.branch_id vs employee.branch_id (need to verify)
Department: shift.department_id vs employee.department_id

SHIFT USAGE ACROSS MODULES:

StockOpening:
- Loads current shift with: where('employee_id', auth_user)
                          where('status', 'active')
                          where('shift_date', today())
- Uses shift.shift_type for filtering stock
- Stores sales_shift_id (nullable) in ProductStock
- ❌ ISSUE: Should store shift_id, not sales_shift_id

POS:
- Loads current shift same way
- Checks stock opening exists (no shift requirement)
- Creates sales WITHOUT linking to shift
- ❌ ISSUE: Sets sales_shift_id = null, should be shift.id

ShiftClosing:
- Loads current shift for employee
- Filters sales by shift times OR date
- Inconsistent: uses both clock_in/clock_out AND shift_date
- ❌ ISSUE: Should use shift.clock_in/clock_out consistently

MySales:
- No shift reference at all
- Reports by employee, not by shift
- Could span multiple shifts

FINDING:
Shifts used inconsistently. Some modules link to shift, others ignore it.
Multiple field naming conventions: sales_shift_id vs shift_id.

PRODUCT STOCK DATA MODEL CONSISTENCY
====================================

ProductStock Table Structure (Inferred):
- id, product_id, sales_shift_id (nullable), stock_date, shift_type
- opening_quantity, addition_quantity, closing_quantity
- quantity_sold, amount, total_available
- production_date, expiry_date
- callback_quantity, redress_quantity (from POS code)
- transfer_quantity, glovo_quantity (from POS code)
- notes
- [MISSING] department_id
- [MISSING] is_verified
- [MISSING] verified_by (employee_id)
- [MISSING] verified_at

Usage Patterns:

StockOpening:
- Creates/updates: opening_quantity, addition_quantity, closing_quantity
- Sets: production_date, expiry_date, notes
- Reads: yesterday's closing_quantity

Dispatches:
- Updates: addition_quantity (received + existing)
- Creates if not exists: new ProductStock with initial closing = addition_qty
- ❌ ISSUE: Doesn't account for opening_quantity

POS:
- Reads: closing_quantity (for available quantity)
- Updates: quantity_sold, amount, closing_quantity
- Creates: If dispatch doesn't exist, new ProductStock
- Calls: updateCalculatedFields()

ShiftClosing:
- Reads: opening_quantity, addition_quantity, closing_quantity
- Updates: closing_quantity (actual count), quantity_sold, notes
- Creates: Callbacks for variances

FINDING:
Multiple code paths update ProductStock. Unclear interaction:
1. StockOpening sets initial values
2. Dispatches might add to addition_quantity
3. POS adds to quantity_sold
4. ShiftClosing finalizes closing_quantity

Order/timing critical - race conditions possible.

STOCK ADDITION SOURCES - CONFLICTING DATA
===========================================

Current Implementation Has TWO Sources for Additions:

SOURCE 1: Production Records (StockOpening)
Location: StockOpening/Index.php, lines 256-305
Query: 
  production_records 
  JOIN daily_produces JOIN shifts JOIN recipes
  WHERE recipes.product_name = products.name
  AND shifts.shift_date = today()
Result: $todayAdditions (summed quantity_approved)

SOURCE 2: Product Dispatch (Dispatches Module)
Location: Dispatches/Index.php, receiveDispatch()
Updates: ProductStock.addition_quantity += received_quantity
Also directly updates: ProductStock creation with addition_quantity

CONFLICT:
- StockOpening loads additions expecting 0 dispatches received yet
- But Dispatches module updates addition_quantity as dispatches arrive
- If dispatch received AFTER StockOpening saved, addition not reflected
- If dispatch received BEFORE StockOpening, might be double-counted

Example Scenario:
1. 08:00 StockOpening: loads additions from production_records = 100
   - Saves ProductStock with addition_quantity = 100
2. 10:00 Dispatch arrives: 90 items received
   - Updates ProductStock.addition_quantity += 90 = 190
3. Actual production was 100, but stock shows 190!

FINDING:
Stock additions tracking is broken. Should use single source: ProductDispatch.
Dispatches should be received DURING shift, stocking should track them.

CASH RECONCILIATION CONSISTENCY
===============================

Payment Data Storage (Unclear):

POS System (POS/Index.php):
- Creates Receipt with: 'payments' => $this->payments array
- Payments array: [['method' => 'cash', 'amount' => 100], ...]
- Storage: In Receipt.content (HTML) and Receipt.payments (JSON)
- Creates: Sale record (no payment details)

ShiftClosing (ShiftClosing/Index.php):
- Queries: Payment::whereHas('sale', ...)
- Expects: Payment table with payment_method, amount, status
- Uses: For expected cash/pos/transfer calculation
- Creates: No Payment records (consumes but doesn't feed)

CONFLICT:
- POS creates payment data in Receipt/meta
- ShiftClosing expects Payment table
- Payment table might not exist or be populated
- Two separate payment tracking systems

FINDING:
Payment system needs clarification:
1. Does Payment table exist? If yes: POS must create records.
2. If no: ShiftClosing must read from Receipt JSON.
3. Current state: inconsistent, likely broken.

REPORT GENERATION CONSISTENCY
==============================

MySales (Employee Reporting):
- Cached queries, 5-minute TTL
- Shows: personal sales, top products, hourly/daily trends, payments
- Data: From Sale, SaleItem, Payment (if exists) tables
- No persistence of reports

ShiftClosing (Shift Reporting):
- Calculates: stock, sales, payments, variances
- Data: From ProductStock, Sale, SaleItem, Payment tables
- Stores: In Shift.notes as JSON
- No separate report record

FINDING:
Two reporting systems exist but don't integrate:
- MySales: Employee-level analytics
- ShiftClosing: Shift-level reconciliation
Should have formal ReportingDashboard with:
1. Shift reports (official records)
2. Employee reports (analytics)
3. Department reports (KPIs)
4. Branch reports (executive view)

AUDIT TRAIL & ACCOUNTABILITY CONSISTENCY
=========================================

StockOpening:
- Employee verifies stock
- No tracking: who, when, what changed
- Just saves data, no audit log

POS:
- Employee makes sales
- Only sold_by field tracks employee
- No audit of discounts, voids, refunds

Dispatches:
- Employee receives dispatch
- Tracks received_by
- But no before/after comparison

ShiftClosing:
- Employee closes shift
- No tracking of who closed
- Just saves to shift.notes
- No supervisor review

FINDING:
No audit trail for financial transactions. Critical gaps:
1. Who verified stock and when
2. Why stock counts changed
3. Who entered cash reconciliation
4. Why variances occurred
5. What corrections were made post-close

TIME ZONE & TIMESTAMP CONSISTENCY
==================================

Carbon Usage:
StockOpening:
- Carbon::today() - date only
- No time component, no timezone

POS:
- Carbon::now() - full timestamp with time
- Uses for sale_time

ShiftClosing:
- Carbon::today() - date only
- Carbon::now() - for clock_out timestamp

MySales:
- Various: now(), startOfDay(), endOfDay()
- Multiple timezone conversions

FINDING:
Inconsistent timestamp handling:
- Some use date-only (stock_date)
- Some use timestamp (sale_time, clock_out)
- Some use Carbon formatting (Y-m-d vs Y-m-d H:i:s)
- No timezone consistency

Should standardize:
1. Use timestamps for all transaction times
2. Use dates for grouping/reporting only
3. Handle timezone consistently (app timezone vs user timezone)
