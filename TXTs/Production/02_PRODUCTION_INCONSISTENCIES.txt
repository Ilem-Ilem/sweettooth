🔴 ISSUE #1: INCONSISTENT EMPLOYEE ACTOR PATTERN
Location: ApproveCallbacks.php (line 314-319) vs CreateInventoryCallback.php vs system standard
Severity: HIGH - Breaks polymorphic tracking pattern used throughout codebase

Problem:
--------
ApproveCallbacks.php:
  protected function getEmployeeId()
  {
    return session('employee_id') ?? auth()->user()?->employee_id ?? null;
  }

This returns ONLY an ID, but callbacks use polymorphic relationships:
  recorded_by_id, recorded_by_type
  approved_by_id, approved_by_type
  received_by_id, received_by_type

This method:
  - Doesn't capture the actor TYPE (Employee vs User)
  - Can't be used with polymorphic $actor->id and get_class($actor) pattern
  - Uses session() which is unreliable
  - Inconsistent with current_actor() used everywhere else

System Standard (from codebase):
  function current_actor(): User|Employee|null
  {
    if (auth()->check()) return auth()->user();
    if (auth('employees')->check()) return auth('employees')->user();
    return null;
  }

Compare with correct usage in ProductionCallback model (line 198):
  $actor = $actor ?? current_actor();
  // ... then uses:
  'approved_by_id' => $actor->id,
  'approved_by_type' => get_class($actor),

Impact:
-------
1. polymorphic recordedBy/approvedBy relationships may fail
2. Can't track whether approval came from User or Employee
3. Breaks audit trail requirements
4. Inconsistent with entire codebase patterns

Fix Required:
-------------
Replace getEmployeeId() with proper current_actor() pattern:

    public function approveCallback($callbackId)
    {
        try {
            DB::beginTransaction();
            $callback = ProductDispatchCallback::find($callbackId);
            if (!$callback) {
                $this->toast()->error('Callback not found.')->send();
                return;
            }

            $actor = current_actor();  // ← CHANGE HERE
            if (!$actor) {
                $this->toast()->error('No authenticated actor found.')->send();
                return;
            }

            $callback->approve($actor);  // ← Pass actor object, not just ID
            
            DB::commit();
            $this->toast()->success('Callback approved successfully!')->send();
            $this->dispatch('$refresh');

        } catch (\Exception $e) {
            DB::rollBack();
            $this->toast()->error('Failed to approve callback: ' . $e->getMessage())->send();
        }
    }

Same fix needed for:
  - receiveCallback() (line 189)
  - completeCallback() (line 226)
  - Index.php callback operations

🔴 ISSUE #2: DUPLICATE STOCK UPDATE LOGIC
Location: ApproveCallbacks.php (line 267-312) + ProductDispatchCallback model (line 295-369)
Severity: HIGH - Violates DRY principle, causes bugs, API incompatibility

Problem:
--------
handleStockImpact() in ApproveCallbacks.php (Livewire component):
  - Manually updates ProductStock.callback_quantity
  - Manually updates DailyProduce.callback_quantity + closing_quantity
  - Duplicates completeWithStockUpdate() logic in model

This means:
  1. Stock logic isn't reusable (API calls can't use it)
  2. Can't be tested independently
  3. Difficult to maintain (changes in two places)
  4. Creates transaction inconsistency
  5. completeWithStockUpdate() exists but isn't used

Current flow (WRONG):
  ApproveCallbacks.completeCallback()
    → handleStockImpact($callback)  ← Business logic in UI
    → $callback->complete()         ← Model method for status only

Correct flow should be:
  ApproveCallbacks.completeCallback()
    → $callback->completeWithStockUpdate()  ← Everything in model

Code to Remove (ApproveCallbacks.php lines 267-312):
  protected function handleStockImpact(ProductDispatchCallback $callback): void
  {
    // All this logic should be in model!
  }

Replace with single call:
  $callback->completeWithStockUpdate();

The model already has this correct implementation (line 295):
  public function completeWithStockUpdate(): bool
  {
    if ($this->status !== 'received_by_production') {
        throw new RuntimeException(...);
    }
    return DB::transaction(function () {
        $this->updateProductStock();    // ← Correct
        $this->updateDailyProduce();    // ← Correct
        $this->update(['status' => 'completed']);
        return true;
    });
  }

Impact:
-------
- Stock updates won't work from API layer
- Stock updates won't work from queued jobs
- Difficult to test stock logic independently
- Transaction handling is split between UI and model

⚠️ ISSUE #7: NO BRANCH FILTERING IN CALLBACKS INDEX
Location: Index.php getFilteredQuery() line 60-69
Severity: MEDIUM - Data isolation issue

Current code:
  protected function getFilteredQuery()
  {
    $query = ProductionCallback::query()
        ->with(['item', 'product', 'shift', 'recordedBy', 'approvedBy'])
        ->whereHas('shift', function ($q) {
            $q->where('branch_id', $this->getBranchId());
        });
    return $query;
  }

This is CORRECT - filters through shift.branch_id

But ApproveCallbacks.php getFilteredQuery() (line 62-71) does:
  ->whereHas('productDispatch.salesShift', function ($q) {
      $q->where('branch_id', $this->getBranchId());
  })

Problem: productDispatch is NULLABLE, so this may miss callbacks without dispatch.

Better approach:
  ->whereHas('salesShift', function ($q) {
      $q->where('branch_id', $this->getBranchId());
  })

Or handle both cases:
  ->where(function($q) {
      $q->whereHas('salesShift', fn($sq) => $sq->where('branch_id', ...))
        ->orWhereHas('productDispatch.salesShift', fn($sq) => $sq->where('branch_id', ...));
  })

⚠️ ISSUE #8: NO TRANSACTION HANDLING IN CREATEINVENTORYCALLBACK
Location: CreateInventoryCallback.php submitCallback() line 289-350
Severity: MEDIUM - Partial transaction

Code has DB::transaction but doesn't throw exceptions to roll back:
  
  try {
      DB::beginTransaction();
      // ... validation ...
      ProductionCallback::create([...]);
      DB::commit();  // ← Commits even if validation fails earlier
  }

If validation fails between try and create, transaction still commits nothing.
But better pattern would be:

  try {
      $validated = $this->validate([...]);
      // Validation happens here, can throw ValidationException
      
      $result = DB::transaction(function () use ($validated) {
          return ProductionCallback::create($validated);
      });
  }

This ensures validation happens BEFORE transaction.
