🔑 CORE CONCEPTS
================

1. POLYMORPHIC RELATIONSHIPS
   Both Employee and User can perform actions in callbacks.
   Tracked via: recorded_by_type (full class name) + recorded_by_id (ID)
   Used by: current_actor() and get_class($actor)

2. THREE CALLBACK TYPES
   
   A) ProductionCallback (Production → Inventory)
      What: Report damaged/defective items
      Status: pending → approved_by_inventory → completed
      Flow: Production discovers issue → Inventory approves → Stock updated
   
   B) ProductDispatchCallback (Sales → Production)
      What: Return products from sales to production
      Status: pending → approved_by_production → received_by_production → completed
      Flow: Sales creates return → Production approves → Production receives → Stock updated
   
   C) ProductCallback (LEGACY)
      Status: Not actively used, review for deprecation

3. STOCK UPDATES
   ProductionCallback.approve() - Updates stock immediately
   ProductDispatchCallback.completeWithStockUpdate() - Updates stock on completion

4. ACTOR TRACKING
   All actions tracked with actor polymorphic relationship
   Allows auditing: who created, approved, received callbacks
   Works with both Employee and User models

⚠️ CRITICAL ISSUES AT A GLANCE
==============================

Issue #1: Actor Pattern Inconsistency
  Location: ApproveCallbacks.php, CreateInventoryCallback.php
  Problem: Uses getEmployeeId() instead of current_actor()
  Impact: Breaks polymorphic tracking, User (super admin) approvals not tracked
  Severity: HIGH
  Fix time: 2 hours

Issue #2: Duplicate Stock Logic
  Location: ApproveCallbacks.php handleStockImpact() vs ProductDispatchCallback.completeWithStockUpdate()
  Problem: Stock update logic in both UI and model
  Impact: API calls won't update stock, difficult to maintain, can't test independently
  Severity: HIGH
  Fix time: 1 hour

🎓 KEY TAKEAWAYS
================

1. Polymorphic relationships allow flexible actor tracking
2. Business logic belongs in models, not UI components
3. Stock updates must use transactions to prevent race conditions
4. Use current_actor() for consistent authentication pattern
5. Always store actor type for audit trails
6. Test stock updates independently from UI
7. Branch filtering should include edge cases (NULL references)
