🔴 ISSUE #3: ACTOR PATTERN INCONSISTENCY (STILL EXISTS)
Location: ApproveCallbacks.php, CreateInventoryCallback.php
Severity: CRITICAL - Breaks polymorphic tracking
Scope: Callbacks can involve multiple departments

--------
Still the same issue from original analysis:
  - Uses getEmployeeId() instead of current_actor()
  - Can't track User (super admin) approvals
  - Breaks polymorphic relationship storage

This is NOW EVEN MORE CRITICAL because:
  - Callbacks span production ↔ inventory ↔ sales
  - Multiple departments involved
  - Multiple actor types possible (Employee from different depts, User)
  - Audit trail must track actor type

Fix:
---
See 03_PRODUCTION_IMPROVEMENTS.txt Priority 1
Use current_actor() pattern throughout

Time: 2 hours
Impact: Critical - Required for audit trail integrity


PRIORITY 2: HIGH (Affects Data Integrity)
===========================================

🟠 ISSUE #4: DUPLICATE STOCK LOGIC (STILL EXISTS)
Location: ApproveCallbacks.php handleStockImpact() vs ProductDispatchCallback.completeWithStockUpdate()
Severity: HIGH - Stock updates won't work from API/jobs
Scope: Both callback types

Problem:
--------
Stock update logic exists in both:
  - ApproveCallbacks.php handleStockImpact() (Livewire component)
  - ProductDispatchCallback.completeWithStockUpdate() (Model method)

Result:
  - Stock updates only work from Livewire
  - API endpoints won't update stock
  - Scheduled jobs can't update stock
  - Code duplication

Why worse with dynamic system:
  - Multiple departments means multiple teams can approve
  - API becomes more important for multi-department workflows
  - Callbacks must work from all interfaces

Fix:
---
See 03_PRODUCTION_IMPROVEMENTS.txt Priority 2
Delete handleStockImpact(), use model method only

Time: 1 hour
Impact: High - Required for API compatibility


PRIORITY 3: HIGH (Navigation & UX)
===================================

🟠 ISSUE #5: CALLBACKS NOT HIGHLIGHTED IN NAVIGATION
Location: Branch dashboard blade template (layout)
Severity: HIGH - User doesn't know they're in production
Scope: Non-department-scoped routes

Problem:
--------
Navigation code:

    $OPEN_DEPT = $departments->firstWhere(
        fn($d) => $d->pages->pluck('route_name')->contains($currentRoute),
    )?->id;

This only matches routes in DepartmentPages.

When viewing callbacks:
  - currentRoute = 'branch-dashboard.production.callbacks.index'
  - No DepartmentPage has this route
  - $OPEN_DEPT = null
  - Production section not highlighted

Result:
  - No visual indication of active section
  - User doesn't see they're in Production
  - Navigation collapse/expand broken

Fix:
----
In dashboard template, add special handling:

    $nonDepartmentRoutes = [
        'branch-dashboard.production.callbacks.index',
        'branch-dashboard.production.callbacks.create-inventory',
        'branch-dashboard.production.callbacks.approve-sales-callbacks',
        'branch-dashboard.production.module.index',
        'branch-dashboard.production.module.stock-monitor',
    ];

    $currentRoute = request()->route()?->getName();
    
    $OPEN_DEPT = $departments->firstWhere(
        fn($d) => $d->pages->pluck('route_name')->contains($currentRoute),
    )?->id;
    
    // Highlight Production if on non-department route
    if (in_array($currentRoute, $nonDepartmentRoutes)) {
        $OPEN_PRODUCTION = true;
    }

Time: 1 hour
Impact: High - Critical for navigation UX

🟡 ISSUE #7: DEPARTMENT SCOPE INCONSISTENCY
Location: All callback components
Severity: MEDIUM - Inconsistent data isolation
Scope: Multi-department deployments

Problem:
--------
Callbacks filtered by:
  shift.branch_id

Should consider:
  Which department created callback?
  Should callbacks be visible only to that department?

Currently: All production staff see all callbacks

Options:
  A) Keep current (all production staff see all callbacks)
  B) Scope to department (only that department's staff see)
  C) Allow both (with admin toggle)

Question: By design or oversight?

Design considerations:
  - Inventory approval crosses departments
  - Sales return callback crosses departments
  - Some callbacks shared, some department-specific

Current approach (all visible) makes sense for:
  - Inventory team approving from all departments
  - Production manager reviewing across departments

So this might be CORRECT DESIGN, not a bug.
