PRODUCTION MODULE - DYNAMIC ARCHITECTURE DEEP DIVE
=================================================

CRITICAL INSIGHT: The Production Module Uses Dynamic Navigation!
===============================================================

⚠️ MY PREVIOUS ANALYSIS WAS INCOMPLETE. The system is driven by DepartmentPages,
not static sidebars. This completely changes the architecture understanding.


THE ACTUAL FLOW
===============

1. Production Department Created
   ↓
   DepartmentObserver.created() fires
   ↓
2. Observer Seeds Default DepartmentPages
   ↓
   Creates 19 DepartmentPage records with:
   - name (display name)
   - slug (unique identifier)
   - route_name (Laravel route)
   - icon (UI icon)
   - order (sort order)
   - is_active (visibility flag)
   ↓
3. Dashboard Navigation Reads DepartmentPages
   ↓
   Queries: Department::where(category.name = 'Production')
            ->with('pages', fn($q) => $q->active()->ordered())
   ↓
4. Dynamic Navigation Built From Pages
   ↓
   Groups by Department
   Filters out edit/detail routes
   Renders as nested navigation


KEY MODELS
==========

Department
  ├─ category (DepartmentCategory)
  ├─ branch (Branch)
  ├─ employees (Employee)
  ├─ pages (DepartmentPage) ← SOURCE OF TRUTH FOR NAVIGATION
  ├─ productTypes (ProductType)
  ├─ products (Product, pivot)
  └─ tables (Table)

DepartmentPage
  ├─ department (Department)
  └─ Fillable: name, slug, route_name, icon, order, is_active
  └─ Scopes: active(), ordered()

DepartmentObserver
  └─ created(Department)
       ├─ Auto-generate slug from name
       └─ If category = 'Production', seed 19 default pages


THE DEPARTMENT OBSERVER (App\Observers\DepartmentObserver)
===========================================================

When a Production Department is created:

1. auto-generate slug:
   $department->slug = Str::slug($department->name);
   // "Kitchen Dept" → "kitchen-dept"

2. Seed default pages:
   seedDefaultPages($department)
   
   Creates DepartmentPage records:
   - Products (route: branch-dashboard.production.products)
   - Product Types (route: branch-dashboard.production.product-types)
   - Recipes (route: branch-dashboard.production.recipes.index)
   - Add Recipe (route: branch-dashboard.production.recipes.add)
   - Edit Recipe (route: branch-dashboard.production.recipes.edit)
   - Recipe Detail (route: branch-dashboard.production.recipes.detail)
   - Production Requests (route: branch-dashboard.production.request.index)
   - Daily Produce (route: branch-dashboard.production.daily-produce.index)
   - Raw Material Tracking (route: branch-dashboard.production.raw-material-tracking)
   - Shift Closing (route: branch-dashboard.production.shift-closing.index)
   - Plus 8 Report pages

3. Uses updateOrCreate():
   Updates if (department_id + slug) exists
   Creates if not
   This makes it safe to re-run


THE DASHBOARD NAVIGATION LOGIC
==============================

Location: resources/views/layouts/branch-dashboard.blade.php (or sidebar partial)

Process:

@php
    $employee = Auth::guard('employees')->user();
    $branchId = request()->get('b_id');
    $departments = collect();

    if ($branchId) {
        // 1. Get all Production departments
        $departments = Department::where(
            fn($q) => $q->where('branch_id', $branchId)->orWhereNull('branch_id')
        )
        ->with([
            'category',
            'pages' => fn($q) => $q->where('is_active', true)->orderBy('order')->orderBy('name'),
        ])
        ->get()
        ->filter(fn($d) => $d->category?->name === 'Production')  // Only Production
        
        // 2. Filter out edit/detail pages from sidebar
        ->map(function ($dept) {
            $dept->pages = $dept->pages->reject(
                fn($p) => str_contains($p->route_name, 'edit') ||
                          str_contains($p->route_name, 'detail'),
            );
            return $dept;
        });

        // 3. Determine if Production section should be expanded
        $currentRoute = request()->route()?->getName();
        $OPEN_DEPT = $departments->firstWhere(
            fn($d) => $d->pages->pluck('route_name')->contains($currentRoute),
        )?->id;

        $OPEN_PRODUCTION = $departments->isNotEmpty() || $OPEN_DEPT !== null;
    }
@endphp

// Then render:
<flux:navlist.group heading="Production" icon="o-cog-6-tooth">
    @forelse($departments as $dept)
        <flux:navlist.group heading="{{ $dept->name }}" expandable="{{ current on deptSlug }}>
            @forelse($dept->pages as $page)
                <flux:navlist.item
                    href="{{ branch_route($page->route_name, [
                        'deptSlug' => $dept->slug,
                        'dept_slug' => $dept->slug,
                        'page' => $page->name . '_' . $dept->slug
                    ]) }}"
                    current="{{ request()->get('page') === $page->name . '_' . $dept->slug }}"
                    icon="{{ $page->icon }}"
                >
                    {{ $page->name }}
                </flux:navlist.item>
            @endforelse
        </flux:navlist.group>
    @endforelse
</flux:navlist.group>


WHY THE SIDEBAR IS EMPTY
=========================

ProductionSidebar.blade.php is intentionally empty because:

✅ CORRECT DESIGN:
  - Navigation is built from DepartmentPages
  - Pages are seeded by DepartmentObserver
  - Navigation is dynamic per branch/department
  - Admin can enable/disable pages via is_active flag
  - No hardcoding of menu items

❌ WRONG (What I initially suggested):
  - Create static ProductionSidebar.blade.php
  - Hardcode all menu items
  - Requires code changes to add new departments
  - Not scalable for multi-branch deployments

LIVEWIRE COMPONENTS & DEPT SLUG
================================

Department-scoped components receive deptSlug:

public function mount($deptSlug)
{
    $this->department = Department::whereSlug($deptSlug)->firstOrFail();
    $this->branchId = $this->department->branch_id;
    // Filter data by this department
}

Non-scoped components (callbacks):

public function mount()
{
    // No deptSlug parameter
    // But should still filter by branch
    $this->branchId = request()->get('b_id');
}

WHAT ABOUT CALLBACKS?
====================

⚠️ INCONSISTENCY FOUND:

Callbacks are NOT seeded as DepartmentPages!

Routes:
  /production/callbacks/
  /production/callbacks/create-inventory
  /production/callbacks/approve-sales-callbacks

These are:
  ✅ Department-agnostic (no deptSlug)
  ❌ Not in DepartmentPages (missing from navigation)
  ❌ Not filtered by department (filter by shift.branch_id instead)

This is correct because:
  - Callbacks involve multiple departments (production ↔ inventory ↔ sales)
  - Can't be scoped to single department
  - Should be accessible from any production context

But they should still be in navigation!

OPTIONS:
1. Add callback pages to DepartmentObserver seeding
2. Create separate top-level menu section for callbacks
3. Add callbacks manually to DepartmentPages for each department


THE DEPTSLUG PARAMETER DANCE
============================

In URLs and Links:

Component receives it as:
  public function mount($deptSlug)

Routes pass it as:
  /production/recipes/{deptSlug}

Navigation passes it as:
  branch_route($page->route_name, ['deptSlug' => $dept->slug])

Components access it as:
  $this->department = Department::whereSlug($deptSlug)->first()

OBSERVER RESPONSIBILITIES
==========================

DepartmentObserver handles:

✅ Slug generation:
   if (empty($department->slug)) {
       $department->slug = Str::slug($department->name);
   }

✅ Page seeding:
   if (category.name === 'Production') {
       seedDefaultPages($department);
   }

✅ Idempotent updates:

❓ NOT handled:
   - Callbacks navigation
   - Department-specific customization
   - Page enable/disable logic
   - Custom icons or ordering


POTENTIAL ISSUES WITH CURRENT DESIGN
====================================

1. ⚠️ Callbacks Not in Navigation
   Problem: No callback routes seeded in DepartmentPages
   Impact: Users must manually navigate to callbacks
   Fix: Add callback pages to observer seeding
   
   Pages to add:
   - 'View Callbacks' → branch-dashboard.production.callbacks.index
   - 'Create Inventory Callback' → branch-dashboard.production.callbacks.create-inventory
   - 'Approve Sales Callbacks' → branch-dashboard.production.callbacks.approve-sales-callbacks

2. ⚠️ Kitchen Module Not Seeded
   Problem: KitchenModule routes not in DepartmentPages
   Impact: Kitchen dashboard not accessible from navigation
   Fix: Add to observer:
   - 'Kitchen Dashboard' → branch-dashboard.production.module.index
   - 'Stock Monitor' → branch-dashboard.production.module.stock-monitor

3. ⚠️ Reports All Top-Level
   Problem: Reports are department-scoped but rendered top-level
   Impact: Reports for specific department not clear
   Question: Should reports be per-department or branch-wide?

4. ⚠️ Edit/Detail Routes Filtered Out
   Problem: Navigation manually filters edit/detail routes
   Impact: These pages unreachable from navigation (must use deep links)
   Design: Intentional (avoid cluttering menu)
   Question: Should edit routes have separate permission?

5. ⚠️ No Callbacks in Current Route Detection
   Problem: Navigation doesn't highlight callbacks as active
   Code:
     $OPEN_DEPT = $departments->firstWhere(
         fn($d) => $d->pages->pluck('route_name')->contains($currentRoute),
     )?->id;
   Impact: When viewing callbacks, no department is marked active
   Fix: Add separate handling for non-department-scoped routes

ACTOR PATTERN IN DYNAMIC SYSTEM
================================

The actor pattern issue (current_actor vs getEmployeeId) still exists
but now with department context:

Current problem:
  ApproveCallbacks::approveCallback() uses getEmployeeId()
  Should use: current_actor()

In dynamic context:
  Callbacks span multiple departments
  So actor type (Employee vs User) must be tracked polymorphically
  current_actor() is correct because:
    - Employee from any department can approve
    - User (super admin) can also approve
    - Both must be tracked in polymorphic relationship


DYNAMIC SYSTEM ADVANTAGES
=========================

✅ Scalable: Add new departments, pages auto-seed
✅ Flexible: Enable/disable pages via is_active flag
✅ Maintainable: Pages defined in model, not routes/views
✅ Multi-branch: Different branches have different departments
✅ Ordered: Pages have explicit ordering
✅ Typed: Route names strongly typed in database
✅ Discoverable: Dashboard can list all available pages
