HOW IT ALL WORKS TOGETHER
==============================================================================

1. USER CREATES TRANSACTION
   ↓
2. TRANSACTION MODEL SAVED TO DATABASE
   ↓
3. LARAVEL FIRES MODEL EVENT (e.g., 'updated' event)
   ↓
4. REGISTERED OBSERVER LISTENS TO EVENT
   ↓
5. OBSERVER CHECKS TRIGGER CONDITION
   - Sale: status='completed' AND isFullyPaid()
   - Purchase: status='approved'
   - Payment: status='completed'
   - StockMovement: type='damage' OR type='shrinkage'
   ↓
6. IF TRIGGER MET & NOT ALREADY POSTED (gl_posting_status='pending')
   ↓
7. OBSERVER CALLS GLPOSTINGSERVICE METHOD
   - postSaleTransaction()
   - postPurchaseTransaction()
   - postPaymentTransaction()
   - postInventoryAdjustment()
   ↓
8. SERVICE CREATES GL ENTRIES
   - Debit/Credit entries
   - Updates account balances
   ↓
9. OBSERVER UPDATES TRANSACTION
   - gl_posting_status = 'posted'
   - gl_posted_at = now()
   ↓
10. TRANSACTION FULLY RECORDED IN GL

If error at step 7-8:
- gl_posting_status = 'failed'
- gl_posting_error = error message
- Error logged to storage/logs/laravel.log
- Transaction still saved (non-blocking)
- Admin can retry later

OBSERVER TRIGGER CONDITIONS
==============================================================================

SALE OBSERVER
├── created(): Ignored
│   (Fires on new sale, but not yet completed)
│
└── updated(): 
    ├── Check: status was changed
    ├── Check: new status = 'completed'
    ├── Check: gl_posting_status = 'pending' (not already posted)
    ├── Check: sale->isFullyPaid() returns true
    └── If all checks pass: Post to GL

GL ACCOUNTS REFERENCED
==============================================================================

SALES:
  1010/1050 - Cash/Bank (Debit)
  4010 - Sales Revenue (Credit)
  5010 - COGS (Debit)
  1220 - Inventory (Credit)
  2020 - Sales Tax Payable (Credit) [if tax > 0]

PURCHASES:
  1200 - Inventory (Debit)
  2010 - Accounts Payable (Credit)

PAYMENTS:
  2010 - Accounts Payable (Debit)
  1010/1050 - Cash/Bank (Credit)

ADJUSTMENTS:
  5020 - Damage Loss (Debit) [for damage type]
  5030 - Shrinkage Loss (Debit) [for shrinkage type]
  1220 - Inventory (Credit)

==============================================================================
TROUBLESHOOTING REFERENCE
==============================================================================

Observer Not Firing:
  - Check observer registered in AppServiceProvider
  - Check model event not suppressed
  - Check trigger condition met
  - Check logs for errors

GL Posting Failed:
  - Check accounting period is OPEN
  - Check GL accounts exist and are ACTIVE
  - Check gl_posting_error field for details
  - Check logs: tail storage/logs/laravel.log

GL Not Balanced:
  - Run trial balance query (see docs)
  - Check for duplicate entries
  - Verify entry debit/credit balanced

Missing GL Entries:
  - Verify transaction met trigger condition
  - Check gl_posting_status field
  - Review observer trigger logic
  - Check logs for errors during posting

IMPORTANT NOTES
==============================================================================

1. NO DATA MIGRATION NEEDED
   - All existing transactions have gl_posting_status = NULL
   - Migrate them later if needed (Phase 4)
   - Current implementation only posts NEW transactions

2. BACKWARD COMPATIBLE
   - Old transactions not affected
   - New fields are nullable
   - Can coexist with existing system

3. ERROR HANDLING
   - GL posting errors are non-blocking
   - Transaction saved regardless of GL posting
   - Failed postings can be retried manually

4. PERFORMANCE
   - GL posting happens synchronously
   - Could be made async with queues if needed
   - Typical posting < 100ms per transaction

5. AUDIT TRAIL
   - All GL entries logged with reference
   - Entry status tracks draft→posted→reversed
   - User who posted recorded (entered_by_id)
