PHASE 2: AUTOMATIC JOURNAL ENTRY POSTING (3 weeks)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Priority: HIGH - Critical for data accuracy
Timeline: Weeks 3-5

Objectives:
  - Automate GL posting from transactions
  - Ensure double-entry integrity
  - Maintain GL in real-time sync with operations

Deliverables:
  - GlPostingService class
  - Transaction observers for auto-posting
  - GL balance calculations
  - Posting validation

Tasks:
  1. Create GlPostingService:
     Location: app/Services/GlPostingService.php
     
     Methods:
     - postSaleTransaction(Sale $sale)
       Entry A: debit Cash/Receivable, credit Sales Revenue
       Entry B: debit COGS, credit Inventory
       Entry C: debit Cash/Receivable, credit Sales Tax Payable
     
     - postPurchaseTransaction(Purchase $purchase)
       Entry: debit Inventory, credit Accounts Payable
       (Include allocation of landing costs to each item)
     
     - postPaymentTransaction(Payment $payment)
       Debit: Accounts Payable / Cash
       Credit: Cash / Accounts Payable
     
     - postInventoryAdjustment(StockMovement $movement)
       Debit: Inventory Loss, credit Inventory (for damage)
       Debit: Work in Progress, credit Inventory (for production use)
     
     - postManualEntry(GlEntry $entry)
       Validation: Debit = Credit
       Validation: GL account exists and is active

  2. Create model observers:
     Location: app/Observers/
     - SaleObserver (listen to Sale::created, ->update posting)
     - PurchaseObserver (listen to Purchase::approved)
     - PaymentObserver (listen to Payment::completed)
     - StockMovementObserver (listen to StockMovement::created)

  3. Register observers:
     Location: app/Providers/EventServiceProvider.php
     
     In boot():
     Sale::observe(SaleObserver::class);
     Purchase::observe(PurchaseObserver::class);
     Payment::observe(PaymentObserver::class);
     StockMovement::observe(StockMovementObserver::class);

  4. Create validation rules:
     - GlEntry must balance (debit = credit)
     - Account must be active
     - Period must be open
     - Prevent posting to header accounts

  5. Implement balance updates:
     - After posting, update GlAccount.debit_balance + credit_balance
     - Maintain account totals

  6. Add GL reference to transactions:
     - Update Sale, Purchase, Payment models
     - Add: gl_entry_ids, posted_at, posting_status
     
     Migrations:
     - alter_sales_table_add_gl_reference
     - alter_purchases_table_add_gl_reference
     - alter_payments_table_add_gl_reference

  7. Testing:
     - Test each posting scenario
     - Test GL balances after posting
     - Test with multiple currencies (if applicable)
     - Test with multiple branches

Timeline Estimate: 15 working days
Depends On: Phase 1
Blocks: Phase 3, Phase 4


PHASE 3: GL REPORTS (2 weeks)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Priority: MEDIUM - User-facing reports
Timeline: Weeks 6-7

Objectives:
  - Enable financial statement reporting
  - Support decision-making with GL data
  - Provide audit trail visibility

Deliverables:
  - General Ledger report
  - Trial Balance report
  - Income Statement
  - Balance Sheet
  - Reports UI/Views
  - Export to PDF/Excel

Tasks:
  1. Create report services:
     
     Location: app/Services/Reports/
     
     - GeneralLedgerService
       Methods:
       - getAccountLedger(glAccountId, startDate, endDate)
         Returns all entries for an account with running balance
       - getAllLedgers(glAccountIds, startDate, endDate)
         Returns all accounts' ledgers
     
     - TrialBalanceService
       Methods:
       - generate(accountingPeriodId)
         Returns all accounts with debit/credit totals
         Validates: Total Debits = Total Credits
     
     - IncomeStatementService
       Methods:
       - generate(startDate, endDate, branchId = null)
         Returns:
         - Revenue (4000-4900)
         - COGS (5000-5900)
         - Operating Expenses (6000-6900)
         - Admin Expenses (7000-7900)
         - Finance Costs (8000-8900)
         - Taxes (9000-9900)
         - Net Income
     
     - BalanceSheetService
       Methods:
       - generate(asOfDate, branchId = null)
         Returns:
         - Assets (1000-1900)
         - Liabilities (2000-2900)
         - Equity (3000-3900)
         - Validates: Assets = Liabilities + Equity

  2. Create Livewire components:
     
     Location: app/Livewire/BranchDashboard/Accounting/
     
     Components:
     - GeneralLedgerComponent
       Params: glAccountId, startDate, endDate
       Displays: Entries in table format with running balance
     
     - TrialBalanceComponent
       Params: accountingPeriodId
       Displays: All accounts with debits/credits
     
     - IncomeStatementComponent
       Params: startDate, endDate, branchId
       Displays: Revenue, COGS, Expenses, Net Income
     
     - BalanceSheetComponent
       Params: asOfDate, branchId
       Displays: Assets, Liabilities, Equity

  3. Create views:
     Location: resources/views/livewire/accounting/
     
     Views:
     - general-ledger.blade.php
     - trial-balance.blade.php
     - income-statement.blade.php
     - balance-sheet.blade.php

  4. Add export functionality:
     - Export GL to PDF
     - Export Trial Balance to Excel
     - Export Financial Statements to PDF

  5. Testing:
     - Verify GL balances match account balances
     - Verify TB = Assets + Liabilities + Equity
     - Verify TB debits = credits
     - Test with sample data

Timeline Estimate: 10 working days
Depends On: Phase 2
Blocks: Phase 4

================================================================================
                        RISK MITIGATION
================================================================================

Risk 1: Duplicate entries in GL during transition
  Mitigation:
  - Validate all existing transactions before posting
  - Implement idempotent posting (can't double-post)
  - Use transaction IDs to prevent duplicates

Risk 2: GL doesn't balance
  Mitigation:
  - Implement validation in posting engine
  - GL entry must have debit = credit
  - Journal balancing rules enforced

Risk 3: Posting logic errors
  Mitigation:
  - Comprehensive unit tests for all posting scenarios
  - Test with sample data before going live
  - Thorough code review

Risk 4: Performance issues with large GL
  Mitigation:
  - Index gl_entries table properly
  - Use date range queries (don't load all entries)
  - Archive old entries if needed

Risk 5: User error in manual entries
  Mitigation:
  - Validation rules (must balance)
  - Approval workflow
  - Ability to reverse bad entries
  - Detailed audit trail
